9. **✅ PR #64 — Backfill de contexto do template na primeira resposta do cliente.** Achado testando a #62/#63 em produção: destinatário do disparo em massa não tem `Contact`/`Conversation` até responder de verdade (deliberado); quando responde, o Chatwoot cria a conversa nativa **sem contexto nenhum** — agente vê só "sim, pode ser" sem saber a qual template é resposta.
   - `WhatsappBulkDispatch::ReplyBackfillService`, chamado de `Conversation#after_create` (novo hook em `enterprise/app/models/enterprise/conversation.rb`, arquivo pré-existente sem `self.prepended` até agora): insere o template enviado como mensagem `activity`, datada com o `sent_at` real do recipient, antes da resposta no histórico. Só dentro de `WHATSAPP_BULK_DISPATCH_REPLY_WINDOW_HOURS` (default 24h, janela de atendimento do WhatsApp Cloud API) — passado isso o assunto provavelmente esfriou e o contexto ficaria enganoso. Só vale pro disparo em massa (campanha por etiqueta já parte de contato existente).
   - `message_type: activity` (não `outgoing`) é o que evita qualquer risco: `Message#webhook_sendable?` e `AutomationRuleListener#ignore_message_created_event?` já excluem `activity`, então a nota nunca vira reenvio real, nunca dispara automação/agent bot, nunca gera notificação push duplicada.
   - **Achado de ordering (o bug real desta PR, pego só empiricamente)**: a primeira tentativa hookou `Message#before_create` (pra rodar "antes" da mensagem real). `last_activity_at` da conversa ficava com o horário retroativo do backfill em vez do horário da resposta — o oposto do esperado. Causa raiz: `after_commit`/`after_create_commit` se registram na transação no **início** do próprio `save`/`create!` do registro, não na ordem de INSERT — então criar o backfill de dentro do `before_create` da mensagem real (cujo `save!` já tinha começado) registrava ele **depois**, não antes. Corrigido movendo o hook pra `Conversation#after_create`, que sempre termina antes do `IncomingMessageBaseService` chamar `Message#save!` da resposta real.
   - **Achado descartado antes de codar**: `conversation.messages.empty?` chamado de um `before_create` da própria mensagem sempre retorna `false` (a associação já vê o registro em memória via `.build`) — ficou moot ao mover o hook pra `Conversation`, que é inerentemente vazia no seu próprio `after_create`.
   - Testado via `rails runner` simulando webhook real (`Whatsapp::IncomingMessageWhatsappCloudService`): resposta dentro da janela → backfill correto + `last_activity_at` correto; fora da janela → sem backfill; segunda resposta → sem duplicar.
   - **Confirmado ao vivo pelo usuário (20/07/2026)**: teste real end-to-end (conversa #190) com o BotFlow ativo — a nota de backfill aparece antes do "oi" do cliente, renderiza como nota de atividade (sem bolha de chat, sem nome de remetente) tanto no dashboard quanto no app mobile, e o BotFlow engatou normalmente em seguida sem nenhuma interferência da nota sintética.

## Infraestrutura local (para testar o wizard de verdade)

Stack de dev completa (`docker-compose.yaml`, separado do `docker-compose.production.yml`). Subir com `docker compose -f docker-compose.yaml up -d` — Rails em `localhost:3000`, Vite em `localhost:3036`.

**Vite: rodar nativo no Windows (recomendado).** Bind mount (`./:/app`) num host Windows não propaga evento de mudança de arquivo de forma confiável pro container — sem isso o HMR não pega nada sem rebuild manual + restart. Setup: `docker-compose.override.yml` (gitignorado) aponta `VITE_RUBY_HOST=host.docker.internal`; rodar `pnpm exec vite dev` direto no host. Polling (`CHOKIDAR_USEPOLLING`) fica só como fallback opt-in pro Vite dockerizado — um polling de 100ms cru satura CPU e causa `Net::ReadTimeout`. **Receita completa e atualizada em `.ai/workflow.md`** (10/09/2026): inclui a armadilha do `depends_on: vite`, que fazia o `docker compose up rails` subir o Vite dockerizado junto, e o timeout de 10 ms da checagem do `vite_ruby`, que gerava 404 em rajada.

**Armadilhas:**
- Faltam migrations ao subir pela primeira vez — `bundle exec rails db:migrate` dentro do container `rails`.
- 🔴 **Banco local do zero: usar `db:schema:load`, não `db:migrate`.** Uma migration antiga (2023, `add_cached_labels_list`) não é mais compatível com a versão atual do gem `acts-as-taggable-on` (`ActsAsTaggableOn::Taggable::Cache` não existe mais na API do gem instalado) — `db:migrate` do zero quebra nela. Isso nunca afeta a VM de produção (ela já rodou essa migration há anos, com a versão do gem da época) — só afeta recriar o banco de dev local do zero. `bundle exec rails db:schema:load` carrega direto do `db/schema.rb` e evita reproduzir todo o histórico de migrations.
- Sem inbox de WhatsApp local por padrão — criado `Channel::Whatsapp` fake (`provider: 'whatsapp_cloud'`, credenciais inventadas, `save!(validate: false)`) com template aprovado fake via `update_column(:message_templates, [...])`. Credencial falsa nunca envia de verdade — seguro testar o fluxo inteiro.
- Feature flag `whatsapp_campaign` desligada por padrão na conta local — `account.enable_features('whatsapp_campaign')`.
- `docker compose exec vite pnpm exec vite build` (build completo) + `docker compose restart rails` — necessário pra ver mudança sem o Vite nativo.
- 🔴 Serviço `sidekiq` do `docker-compose.yaml` não tem entrypoint que rode `bundle install` sozinho (diferente de `rails`/`vite`). Depois de mexer no `Gemfile`, container crash-loopava. Fix: `docker compose run -d --name chatwoot-develop-sidekiq-1 --entrypoint sh sidekiq -c "bundle install && bundle exec sidekiq -C config/sidekiq.yml"`.
- `annotate` roda sozinho no `db:migrate` local e reescreve comentário de schema em QUALQUER model — revelou que `db/schema.rb` do repo estava desatualizado vs. schema real da VM (faltavam `captain_sentiment`, `deleted_at`). **Corrigido de brinde no upgrade v4.16.1** (27/07/2026, ver `.ai/archive/2026-07-misc.md`) — `db/schema.rb` foi regenerado rodando as migrations de verdade num banco vazio em vez de mesclado como texto no conflito do merge.

**Dados de teste locais:** um dispatch de teste (`WhatsappBulkDispatch#1`, "Teste", status `completed`, 2 recipients ambos `failed` por credencial fake) foi deletado direto via `rails runner` em 20/07/2026 a pedido do usuário, pra ver o estado vazio real — bypassando de propósito a regra de UI que bloqueia exclusão de `completed` (regra é pra uso normal, não pra limpeza de dado de teste local).
