## Instance Status: Blob Storage + Disco (PR #39)

Duas métricas em `/super_admin/instance_status` (`SuperAdmin::InstanceStatusesController`, adicionar métrica = 1 método):
```
Blob storage (AzureStorage)  | 6.47 MB in 12 files
Disk                         | 9.17 GB / 61.8 GB (14.8%)
```
Produção: `ACTIVE_STORAGE_SERVICE=microsoft` → Azure Blob (conta `chatwootuh3q3d`, container `chatwoot`) guarda anexos do WhatsApp; disco da VM guarda Postgres/Redis/imagens Docker.

- Blob "usado" = `ActiveStorage::Blob.sum(:byte_size)` (1 query, instantâneo) — **de propósito não chama a API da Azure** (listar pagina o container inteiro, travaria a página). Azure Blob não tem cota por container — não existe teto real pra mostrar.
- Disk: `df -kP /` dentro do container reporta o filesystem do overlay = disco da VM (verificado, bate com o host). É o único que enche e derruba a instância.

**Housekeeping feito no mesmo dia:** `docker image prune -a -f` (sem `--volumes`) liberou 23GB→9.2GB (37%→15%). O grosso era imagem parada (`typebot-builder`/`typebot-viewer`, descontinuados, e a imagem oficial `chatwoot/chatwoot` — rodamos o fork `ghcr.io/mobillirentals/chatwoot`). **Recorrente:** cada deploy empilha imagem nova, vale rodar o prune periodicamente.

## Upgrade Chatwoot v4.15.1 → v4.16.1 (27/07/2026)

Branch `upgrade/v4.16.1` = merge da tag sobre `deploy/develop` (PR #65). Ao contrário do upgrade anterior, **não foi conflito-zero**: `git merge-tree --write-tree` (simulação real, só leitura) apontou 9 conflitos — `premium_features.yml`/branding/ícones (triviais, nosso lado venceu), `lib/redis/redis_keys.rb` (união), `agent_tools`/`event_data_presenter` (reconciliação manual, achados abaixo), `db/schema.rb` (não mesclado como texto — regenerado rodando as 22 migrations num banco real, o que também corrigiu de brinde um drift que já existia antes do upgrade), e `enterprise/lib/captain/prompts/assistant.liquid` (reconciliação de comportamento, commit isolado — ver `.ai/features/captain/status.md`).

**🔴 Incidente (resolvido): migration não rodou antes do restart em produção — terceira vez que isso acontece.** O usuário aprovou o "Review deployments" do GitHub Actions (fluxo normal), que faz `pull` + `up -d` — mas **não roda migration**. `needs_migration?` confirmou `true` com o código novo já no ar. Rodado `db:migrate` manual (`--env-file .env.production`) logo em seguida, sem incidente maior desta vez porque nenhuma query orgânica bateu ainda nas colunas/tabelas novas. Mesma causa-raiz do incidente já documentado na lixeira (`.ai/features/trash/status.md`) e do incidente de Redis (regra de ouro em `.ai/workflow.md`) — **CI nunca roda migration, sempre manual, sempre depois de QUALQUER deploy que tenha migration nova.** Vale checklist fixo daqui pra frente: depois de aprovar o deploy, checar `needs_migration?` antes de considerar o deploy terminado.

**Gotcha de ambiente local: imagem `chatwoot:development` buildada com `BUNDLE_WITHOUT=development:test`** (config de produção) em vez do vazio que `docker-compose.yaml` pede via build arg — quebrava o boot do Puma local (`listen` não instalado, gem do grupo `development`). Causa: a imagem base não tinha sido rebuildada há tempo suficiente pra pegar o ARG certo (cache do Docker aceitou um build antigo). Fix: `docker compose build --no-cache base` + rebuild de `rails`/`vite` em cascata. Lembrete: `BUNDLE_PATH=/gems` (Dockerfile) **não é** o volume nomeado `bundle:/usr/local/bundle` do compose (esse volume é morto/não usado) — gem instalada via `docker compose exec ... bundle install` num container vivo só persiste nAQUELE container, se ele for recriado (`up -d`, `run`) a gem some. Só um rebuild de imagem persiste de verdade.

**Achado de roteamento de modelo do Captain e correção de um erro meu no mesmo dia** — ver `.ai/features/captain/status.md`, entrada 27/07/2026: upstream unificou escolha de modelo num router novo que, sem override, forçaria `gpt-5.2` no bot orquestrador (conta tem `captain_integration_v2`) e no gerador de FAQ de conversas — dois overrides aplicados via `account.captain_models` pra preservar o comportamento medido/tunado antes do upgrade. Cometi um erro na primeira tentativa (setei `gpt-5-mini` em vez de `gpt-4.1-mini`, por confiar de cabeça num PR antigo do `status.md` sem checar o valor real em produção) — corrigido no mesmo dia.
